Scenario A — Revision-aware similarity

Participant prompt / query

What calculation downweights chunks from older revisions during search?

Answer key: associated code

File: GitTrace/chunkdb/chunkdb.cpp, lines 230–245. Commit: d77c3ccebcd22970ed4b21c58d35a810b60fa72b.


std::vector<ChunkMatch> ChunkDB::search(const std::string& query, std::size_t k)
{
    const std::vector<float> query_embedding = embed(query, true, false);
    if (query_embedding.empty() || k == 0) return {};

    std::vector<ChunkMatch> matches;
    matches.reserve(chunks.size());
    for (const Chunk& chunk : chunks) {
        const float decay = std::exp(-0.12f * static_cast<float>(chunk.lineage_depth));
        matches.push_back({&chunk, cosineSimilarity(query_embedding, chunk.embedding) * decay});
    }
    std::sort(matches.begin(), matches.end(), [](const ChunkMatch& lhs, const ChunkMatch& rhs) {
        return lhs.similarity > rhs.similarity;
    });
    if (matches.size() > k) matches.resize(k);
    return matches;
}


Expected evidence: similarity is cosine similarity multiplied by exp(-0.12 * lineage_depth), so greater lineage depth reduces the score.

Observed retrieval: The default phrasing did not return the target in top 10. A code-focused query naming lineage_depth returned this chunk at rank 10 (0.2856).

These are broad, remembered-concept searches rather than answer-key searches. In this run, git grep located B–D's implementation evidence; A's remembered terms found the README explanation but missed the code that applies the score adjustment. git grep does not rank results, and -E treats the listed terms as alternatives, so broad terms produce noise. Present the exact keywords to participants and score whether they can locate and verify the implementation, separately from GitTrace's natural-language retrieval ranking.
